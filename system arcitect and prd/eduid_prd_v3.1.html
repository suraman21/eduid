01

SaaS Architecture — Centralized from Day One

Why This Changed

The v2 PRD chose per-school installation. That model breaks when your main revenue is printing — you need server access to generate print files, you manage hosting anyway, and updating 10 separate servers is a nightmare. Full SaaS solves everything: one server, you control it, schools access via browser, print files stay on your server, updates deploy once.

How It Works

  • One VPS, all schools: All school data lives on a single Arkeon-managed VPS (Contabo or DigitalOcean). Each school is isolated by school_id on every database table.
  • School access: Schools log in at app.eduid.et (or eduid.arkeonethiopia.com). They enter their school code at login. No subdomains needed for Phase 1 — one login page, school code as identifier.
  • Teacher app: Flutter app connects to the same central server. Teacher enters school code + credentials on first login.
  • Data isolation: The BelongsToSchool trait on every model auto-scopes all queries by school_id. School A cannot see School B's data — enforced at the ORM level, not just the UI.
  • Backups: One nightly mysqldump + photo backup. You manage it. No reliance on school IT staff.
  • Updates: You deploy once to one server. All schools get the update immediately. No ZIP files, no per-school migration scripts.

Calendar System — Configurable Per School

The schools table has a calendar_system field: 'ethiopian' or 'gregorian'. The Super Admin sets this during school creation. All date displays — dashboard, reports, card validity, Flutter app — respect this setting. Database always stores Gregorian dates regardless. International schools in Ethiopia use Gregorian. Local schools use Ethiopian. The system supports both without code changes.

Card Printing Service — Core Revenue Engine

The Golden Rule

The system NEVER generates a downloadable, printable PDF. Schools see a low-resolution card PREVIEW on screen. The high-resolution print-ready layout is generated server-side only, accessible only to Super Admin (you). This is not a limitation to apologize for — it's a premium service: "We handle everything. Professional PVC cards delivered to your door."

Card Order Flow — With Confirmation Code

1
School Admin clicks "Order Cards"
Selects students: all students, by class, or individual. Sees a low-res preview of each card. Confirms the order.
2
System generates a Confirmation Code
Unique code like ORD-AIA-2026-0847. Displayed to the school admin with message: "Share this code with Arkeon to confirm your order." Order status: Pending.
3
School shares the code via WhatsApp/Telegram/Phone
School admin sends: "Our order code is ORD-AIA-2026-0847, 312 cards." This creates a trust moment — the school is in control, they initiated the order.
4
You (Super Admin) enter the code in your dashboard
Super Admin panel has "Process Card Order" → enter code → system shows: school name, student count, preview, amount due. You click "Confirm & Generate Print Files." Status: Confirmed.
5
System generates high-res print files (server-side only)
TCPDF generates print-ready PDF with exact CR80 card dimensions, arranged for your PVC card printer. Files stored at storage/app/print_jobs/{order_code}/ — never accessible via web URL.
6
You print and ship
Print on PVC card printer. Package cards. Ship/deliver to school. Update status: Printing → Shipped → Delivered. School admin sees status update in their dashboard in real-time.

Why Schools Cannot Print Themselves

  • They never see the print-ready PDF file — only a low-res screen preview
  • Even if they screenshot the preview, PVC card printing requires a specialized printer ($1,500+) that no school owns
  • Paper lamination looks visibly cheap next to a proper PVC card — schools WANT the professional quality
  • QR tokens expire annually — schools MUST order new cards each year or attendance scanning stops working
  • Ordering through the system is easier than DIY — one click, cards arrive at their door

Photo Management System

Getting 500 student photos correctly linked to the right student records is the biggest onboarding challenge. Three methods, from best to simplest:

Method 1: Photo Session Mode (Recommended)

Like School Picture Day

This is the recommended method for initial bulk photography. It's a guided workflow that eliminates photo-to-student mismatches.

1
Admin creates a Photo Session
Selects which class (or whole school). System generates an ordered queue of students sorted alphabetically. Prints a simple checklist: student name + UID, one per line.
2
Students line up in order
Using the printed checklist, students queue in alphabetical order. Teacher checks each name as they step forward.
3
Photographer captures via app or uploads
Option A: Photographer uses the Flutter app's Photo Session screen — shows the current student's name, taps "Capture," camera opens, photo auto-linked. Tap "Next" for the next student. Option B: Photographer uses any camera, names files sequentially (001.jpg, 002.jpg...), uploads ZIP later — system matches by sequence order to the queue.
4
Review & confirm
Admin reviews: each student's name next to their photo. Can swap any mismatches. Once confirmed, session is marked complete. Photos compressed (500KB max) and stored.

Method 2: Bulk Upload by Student UID

If the school already has digital photos, they rename each file to the student's UID: AIA-2026-000412.jpg. Upload a ZIP file → system matches filenames to UIDs automatically. Unmatched photos flagged for manual review. This is best for schools that already have professional photos from a studio.

Method 3: Individual Upload

Admin opens each student's profile, clicks "Upload Photo." Best for small batches, new students mid-year, or photo updates. This is the slowest method but always available as a fallback.

Cards Without Photos Are Allowed

If photos aren't ready yet, cards can still be ordered and printed with a placeholder silhouette icon. Don't block onboarding because photography isn't complete. Schools can order replacement cards with photos later.

Student UID Generation

// Format: {SCHOOL_CODE}-{YEAR}-{6-DIGIT-SEQ} // Example: AIA-2026-000412 public function generateUID(School $school): string { $year = date('Y'); // enrollment year, Gregorian $prefix = "{$school->code}-{$year}-"; $lastStudent = Student::where('uid', 'LIKE', $prefix . '%') ->orderBy('id', 'desc') ->first(); $nextNum = $lastStudent ? intval(substr($lastStudent->uid, -6)) + 1 : 1; return $prefix . str_pad($nextNum, 6, '0', STR_PAD_LEFT); } // Uniqueness: enforced by UNIQUE constraint on uid column // Collision prevention: sequential within school+year prefix // Max capacity: 999,999 students per school per year

Calendar Conversion

Implementation

Use the andegna/calends PHP package for Ethiopian ↔ Gregorian conversion on the backend. In Flutter, use a custom EthiopianCalendar utility class (same JDN algorithm proven in the WBSS app — passes 10,000/10,000 random date tests). All dates stored in MySQL are Gregorian. Conversion happens at the display layer only: Blade views check $school->calendar_system before formatting dates. The Flutter app stores the school's calendar setting locally and converts dates before display.

QR Token Lifecycle

Each student's QR code encodes a cryptographic token that proves identity and is tied to a specific academic year. When a teacher scans the QR code, the system can verify the student is real, active, and enrolled for the current year — without needing an internet connection for basic validation.

Token Generation (Server-Side)

// Generated when: student is created, or during annual year promotion // Each school has a unique HMAC secret (schools.hmac_secret) public function generateQRToken(Student $student): string { $school = $student->school; $payload = "{$student->uid}|{$school->academic_year}"; $token = hash_hmac('sha256', $payload, $school->hmac_secret); // Store on student record $student->update([ 'qr_token' => $token, 'qr_token_year' => $school->academic_year, ]); // QR code encodes: "{UID}|{TOKEN}" // Example: "AIA-2026-000412|a3f7c9e2b1d8..." return "{$student->uid}|{$token}"; } // Security properties: // - Token is unique per student + academic year // - Cannot be forged without the school's HMAC secret // - Old year tokens automatically fail verification // - Each school has a different secret → cross-school forgery impossible

Token Verification

// SERVER VERIFICATION (when online): // POST /api/v1/attendance/verify-qr { qr_data: "AIA-2026-000412|a3f7c9..." } // 1. Split qr_data by "|" → uid, submitted_token // 2. Find student by uid (auto-scoped to teacher's school) // 3. Recompute: expected = HMAC(uid + school.academic_year, school.hmac_secret) // 4. If submitted_token === expected → VALID (student is real, current year) // 5. If mismatch → check if token matches PREVIOUS year → "Card expired, needs renewal" // 6. If no match at all → "Invalid card" // FLUTTER SOFT-CHECK (when offline): // App caches student list with qr_token on last sync // On scan: find student by uid in SQLite, compare cached token // This catches obviously fake/expired cards offline // Full server verification happens when attendance syncs

Annual Renewal (Year Promotion)

  • During Academic Year Promotion Wizard, ALL students get new QR tokens for the new year
  • Old tokens become invalid immediately — old cards stop scanning
  • This forces annual card renewal (new cards with new QR codes = recurring revenue)
  • Schools MUST order new cards each year or attendance scanning breaks
  • The HMAC secret itself stays the same — only the academic_year in the payload changes

Offline Sync Protocol

The Flutter app stores attendance data locally in SQLite when offline. When internet connectivity returns, it syncs automatically in the background. The protocol is designed to be idempotent — sending the same data twice never creates duplicates.

Sync Flow

// 1. Teacher takes attendance offline // → Stored in SQLite: attendance_sessions + attendance_records // → Each session gets a UUID idempotency_key (generated on phone) // → Status: "pending_sync" // 2. App detects internet connectivity // → SyncService triggers automatically (also manual button available) // → Collects all "pending_sync" sessions // 3. Batch POST to server POST /api/v1/attendance/sync { "sessions": [ { "idempotency_key": "a1b2c3d4-...", "class_id": 15, "session_date": "2026-09-15", "session_type": "morning", "method": "qr_scan", "device_id": "samsung-a54-xyz", "records": [ { "student_id": 412, "status": "present", "scanned_at": "2026-09-15T08:32:00" }, { "student_id": 413, "status": "absent" }, { "student_id": 414, "status": "late", "scanned_at": "2026-09-15T08:55:00" } ] } ] } // 4. Server processes each session: // → Check idempotency_key: if already exists → skip (return "already_synced") // → Validate class_id belongs to teacher's school // → Validate all student_ids belong to the class // → Create attendance_session + attendance_records in a transaction // → Return: { synced: 1, skipped: 0, failed: 0 } // 5. App marks synced sessions as "synced" in SQLite // → Failed sessions stay as "pending_sync" for retry // → After 3 consecutive failures → mark as "sync_failed" + alert teacher

Conflict Resolution

  • Same class, same date, same type: Server rejects duplicate via UNIQUE constraint on (school_id, class_id, session_date, session_type). App receives clear error: "Session already exists."
  • Two teachers scanning same class simultaneously: First sync wins. Second gets conflict error → teacher can review and merge manually.
  • Phone clock wrong: Server uses scanned_at from phone (for sequence accuracy) but created_at from server clock (for record-keeping).
  • Offline for days: All pending sessions queue up. Sync processes them oldest-first. No data loss regardless of offline duration.
  • App deleted and reinstalled: Unsynced data is lost. Teacher sees warning when >10 sessions are pending: "Sync now to avoid data loss."

Data Refresh (Server → App)

// On each successful sync, app also pulls fresh data: GET /api/v1/sync/pull?last_sync=2026-09-14T18:00:00 // Returns: updated students, new students, class changes, // deactivated students, new QR tokens // App updates local SQLite cache // Photos: only download if student.updated_at > cached version

Error Handling & Edge Cases

Photo Session Conflicts

  • Two sessions for same class: System prevents creating a new active session if one already exists for the same class. Error: "An active photo session already exists for Grade 9A. Complete or cancel it first."
  • Session interrupted (photographer leaves mid-session): Session stays "active" with photos_captured tracking progress. Photographer can resume anytime. Sessions auto-expire after 7 days of inactivity → status changes to "cancelled."
  • Wrong photo taken: Photographer can tap "Back" to return to previous student and retake. Admin can also manually reassign photos in the review screen before confirming.

Card Order Edge Cases

  • Order cancellation: School Admin can cancel a "pending" order (before Super Admin confirms). Super Admin can cancel any order in "pending" or "confirmed" status. Once "printing" starts, cancellation requires Super Admin to manually update. Status becomes "cancelled" with a cancel_reason.
  • Students without photos: System warns "12 students have no photo" during order creation. School Admin can choose: include them (printed with silhouette placeholder) or exclude them from this order.
  • Student removed after order placed: If a student is deactivated after being included in a pending order, Super Admin sees a warning during confirmation. Can proceed (card printed anyway) or remove student from the order.
  • Duplicate orders: System warns if students are already in an active (non-delivered, non-cancelled) order: "These 15 students are already in order ORD-AIA-2026-0844."

Validate-All-Then-Import

CSV import uses a two-pass strategy. Pass 1: validate every row and collect all errors. Display errors with row numbers: "Row 47: invalid gender 'M' (must be 'male' or 'female')." Pass 2: import only happens after ALL rows pass validation — never partial imports. This prevents orphan data and makes it safe to re-upload after fixing errors.

Password Reset Flow

  • School Admin resets teacher password: Admin goes to teacher management → "Reset Password" → system generates a temporary password → shows it once → teacher must change on first login.
  • Super Admin resets School Admin password: Same flow from Super Admin panel.
  • Self-service password reset: Phase 1 does NOT include email-based reset (Ethiopian schools often lack reliable email). Reset is always through the admin hierarchy. Phase 2 could add Telegram-based reset.
  • Account lockout: After 5 failed login attempts, account is locked for 30 minutes. locked_until timestamp in users table. Admin can unlock immediately via teacher management.

Security Specification

Authentication & Authorization

  • Web panel: Laravel session-based auth with CSRF tokens on every form. Session lifetime: 2 hours idle, 8 hours absolute.
  • Flutter API: Laravel Sanctum token auth. Tokens expire after 30 days of inactivity. Device-bound (one token per device name).
  • Super Admin: Separate login route (/admin/login). Not accessible via school-code login. IP whitelist optional.
  • Password storage: bcrypt with cost factor 12. No plain-text passwords anywhere, including logs.

Data Protection

  • CORS: API allows only app.eduid.et origin + Flutter app (via Sanctum token). No wildcard origins.
  • CSP headers: default-src 'self'; script-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'
  • XSS: All output escaped via Blade's {{ }} syntax. Raw output ({!! !!}) never used with user data.
  • SQL injection: All queries via Eloquent ORM. No raw SQL except in migrations.
  • File uploads: MIME type validation (not just extension). Max 10MB per photo. Only JPEG/PNG/WebP accepted. Files stored outside web root at storage/app/.
  • Photo access: Served through authenticated controller routes only. Direct URL access to /storage/ blocked by Nginx config.
  • Print files: Stored at storage/app/print_jobs/. Accessible ONLY via Super Admin authenticated route. Never linked publicly.

Software Stack on VPS

  • OS: Ubuntu 22.04 LTS (or 24.04)
  • Web server: Nginx (not Apache — lighter, faster for PHP-FPM)
  • PHP: 8.2+ with FPM. Workers: start with 8, scale to 30 at Enterprise tier.
  • Database: MySQL 8.0 with InnoDB. Buffer pool: 25% of total RAM.
  • Cache: Redis for session storage and queue jobs. 256MB–1GB allocation.
  • Queue: Laravel Queue with Redis driver. For attendance sync processing and PDF generation.
  • SSL: Let's Encrypt (free). Auto-renewal via certbot.
  • Firewall: UFW — only ports 22 (SSH), 80 (HTTP), 443 (HTTPS) open.
  • Backup: Nightly mysqldump + rsync photos to backup directory. Keep 7 days.

Storage Calculation

Student photos dominate storage. At ~500KB per compressed photo: 1,000 students = 500MB photos. 10,000 students = 5GB photos. Generated print PDFs add ~2MB per batch. With 10,000 students and generous overhead, you need ~20GB for data + photos. The rest is OS + application. 50GB SSD is enough for the first 5,000 students.
