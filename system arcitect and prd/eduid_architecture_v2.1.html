Executive Summary

EduID is a centralized SaaS platform where Arkeon Ethiopia manages a single VPS running Laravel + MySQL. All schools access the same server — isolated by school_id on every database table. The core revenue is a card printing service: schools order professional PVC ID cards through the system, Arkeon prints and ships. The system never generates downloadable print files. Students are registered via CSV import or manual entry. Photos are captured via a structured Photo Session workflow. Attendance is tracked via QR scanning on a Flutter app that works 100% offline.

What Changed from Architecture v2.0

  • QR Token lifecycle fully specified — HMAC-SHA256 generation, server + offline verification, annual renewal. No longer references v1.
  • Offline sync protocol fully specified — idempotent batch POST, conflict resolution, retry logic, data refresh. No longer references v1.
  • API endpoints: 42 → 46 — added: health check, order cancellation, password reset, photo session conflict check.
  • Table count corrected: 13 → 12 — migrations is Laravel framework infrastructure, not an application table.
  • Security hardening specified — CORS, CSP, rate limiting, account lockout, file upload validation.
  • Photo session conflict prevention — system blocks duplicate active sessions for the same class.
  • Order cancellation flow — new status + API endpoint for cancelling pending/confirmed orders.

Previous Changes (v1 → v2.0)

  • SaaS from day one — single VPS replaces per-school installations. No deployment scripts, no per-school migrations.
  • Card Order System — replaces PDF generation. New card_orders table with confirmation codes and order tracking.
  • Photo Session System — structured photography workflow with queue management. New photo_sessions table.
  • Multi-tenant middleware — SchoolScope middleware auto-filters all queries. BelongsToSchool trait on every model.
  • School-code login — schools log in with school code + email + password. No subdomains in Phase 1.
  • Configurable calendar — calendar_system field on schools table. Ethiopian or Gregorian per school.

Multi-Tenant Design

Login Flow — School Code

// Login page: app.eduid.et/login // Fields: School Code, Email, Password POST /login { school_code: "AIA", // identifies which school email: "admin@school.et", password: "..." } // Backend: 1. Find school by code → school_id = 12 2. Find user by email WHERE school_id = 12 3. Verify password 4. Set session with school_id = 12 5. All subsequent queries auto-scoped to school_id = 12 // Flutter API login: POST /api/v1/auth/login { school_code: "AIA", email: "teacher@school.et", password: "...", device_name: "Samsung A54" } // Returns: { token, user, school: { id, name, code, calendar_system } }

BelongsToSchool Trait

// app/Traits/BelongsToSchool.php trait BelongsToSchool { protected static function bootBelongsToSchool() { // Auto-scope all queries by school_id static::addGlobalScope('school', function ($query) { if (auth()->check() && auth()->user()->role !== 'super_admin') { $query->where('school_id', auth()->user()->school_id); } }); // Auto-set school_id on create static::creating(function ($model) { if (auth()->check() && !$model->school_id) { $model->school_id = auth()->user()->school_id; } }); } } // Usage: add to every model that has school_id class Student extends Model { use BelongsToSchool, SoftDeletes; }
Security Guarantee

With this trait on every model, it is architecturally impossible for School A to query School B's data — even if a developer forgets a WHERE clause. The global scope is enforced at the Eloquent ORM level. Only Super Admin bypasses it (no school_id filter). This is your data isolation guarantee.

Card Order System — Technical Design

Order Code Generation

// Format: ORD-{SCHOOL_CODE}-{YEAR}-{SEQUENTIAL} // Example: ORD-AIA-2026-0847 public function generateOrderCode(School $school): string { $year = date('Y'); $prefix = "ORD-{$school->code}-{$year}-"; $lastOrder = CardOrder::where('order_code', 'LIKE', $prefix . '%') ->orderBy('id', 'desc') ->first(); $nextNum = $lastOrder ? intval(substr($lastOrder->order_code, -4)) + 1 : 1; return $prefix . str_pad($nextNum, 4, '0', STR_PAD_LEFT); }

// When Super Admin confirms an order: // 1. Generate high-res PDF with TCPDF // 2. Store at storage/app/print_jobs/{order_code}/cards.pdf // 3. Photo Management — Technical Design

Photo Session Queue

// When a Photo Session is created for Grade 9A: // 1. Query all students in Grade 9A, sorted alphabetically // 2. Store ordered list as JSON in student_queue column // 3. Track current position (photos_captured count) // Flutter Photo Session Screen: // Shows: "Student 12 of 38: Kidus Tesfaye (AIA-2026-000412)" // Camera button → captures → auto-uploads → advances to next // Skip button → marks as "no photo" → advances // Back button → go to previous student to retake // Sync: photos upload immediately if online, // queue locally if offline (same sync mechanism as attendance)

Photo Processing Pipeline

  • Upload: Accept JPEG, PNG, WebP. Max 10MB raw upload.
  • Validate: Check MIME type (not just extension). Reject non-image files.
  • Resize: Scale to 600×800px (portrait). Crop center if aspect ratio doesn't match.
  • Compress: JPEG quality 80%. Target: under 500KB per photo.
  • Store: storage/app/photos/{school_id}/{student_uid}/photo.jpg
  • Serve: Through auth-protected controller route only. Direct URL access blocked.
  • Cache: Flutter app downloads photos once, caches locally. Refreshes when updated_at changes.

Session Conflict Prevention

No Overlapping Sessions

Before creating a new photo session, the system checks: SELECT * FROM photo_sessions WHERE class_id = ? AND status = 'active'. If an active session exists for the same class, creation is blocked with error: "An active session already exists for this class. Complete or cancel it first." Whole-school sessions (class_id = NULL) block ALL class-specific sessions and vice versa.

  • Auto-expiry: Sessions with status "active" and no activity for 7 days → automatically set to "cancelled" by a daily scheduled task.
  • Resume: Photographer can resume an active session — app loads from current_position in the queue.
  • Concurrent capture blocked: Only one device can capture for a session at a time. Second device gets: "Session in use by another device."

Offline Sync Protocol

Sync Architecture

// OFFLINE STORAGE (Flutter SQLite): // - attendance_sessions (local copy) // - attendance_records (local copy) // - students cache (read-only, refreshed on sync) // - sync_queue (tracks what needs uploading) // SYNC STATES per session: // pending_sync → syncing → synced | sync_failed // TRIGGER CONDITIONS: // 1. Automatic: ConnectivityService detects wifi/mobile data // 2. Manual: Teacher taps "Sync Now" button // 3. Periodic: Every 15 minutes if sessions are pending

Upload Protocol (App → Server)

POST /api/v1/attendance/sync Authorization: Bearer {sanctum_token} { "sessions": [ { "idempotency_key": "uuid-v4-generated-on-phone", "class_id": 15, "session_date": "2026-09-15", // Gregorian always "session_type": "morning", "method": "qr_scan", "device_id": "samsung-a54-imei-hash", "records": [ { "student_id": 412, "status": "present", "scanned_at": "2026-09-15T08:32:00Z" }, { "student_id": 413, "status": "absent", "scanned_at": null }, { "student_id": 414, "status": "late", "scanned_at": "2026-09-15T08:55:00Z", "note": "arrived late" } ] } ] } // RESPONSE: { "results": [ { "idempotency_key": "uuid-...", "status": "synced", "server_id": 847 }, { "idempotency_key": "uuid-...", "status": "duplicate", "server_id": 845 }, { "idempotency_key": "uuid-...", "status": "failed", "error": "Class not found" } ], "synced": 1, "skipped": 1, "failed": 1 } // SERVER PROCESSING (per session): // 1. Check idempotency_key → if exists, return "duplicate" (skip) // 2. Validate teacher has access to class_id (via teacher_classes) // 3. Validate all student_ids belong to class // 4. Check UNIQUE(school_id, class_id, session_date, session_type) // 5. Wrap in DB transaction: create session + all records // 6. If any step fails → rollback entire session, return error

Download Protocol (Server → App)

// After upload sync completes, app pulls fresh data: GET /api/v1/sync/pull?last_sync=2026-09-14T18:00:00Z // Returns only records updated since last_sync: { "students": [ /* new or updated students */ ], "deactivated_student_ids": [501, 502], "classes": [ /* new or updated classes */ ], "school_config": { "academic_year": "2026/2027", "calendar_system": "ethiopian" }, "server_time": "2026-09-15T10:00:00Z" } // App updates local SQLite, sets last_sync = server_time // Photos: check student.updated_at > cached; if newer, re-download // GET /api/v1/students/{id}/photo (auth required, returns compressed JPEG)

Edge Cases

  • Two teachers, same class: First sync wins. Second gets UNIQUE constraint error → app shows "Session already recorded by another teacher."
  • Phone clock wrong: scanned_at from phone (relative accuracy), created_at from server (absolute accuracy).
  • App killed mid-sync: Idempotency key prevents duplicates. Pending sessions retry on next sync.
  • Offline for weeks: All sessions queue locally. Sync processes oldest-first. No data loss.
  • Retry limit: After 5 consecutive failures for same session → mark "sync_failed" → show alert with option to retry or discard.

QR Token Lifecycle

Token Generation

// Each school has a unique HMAC secret (schools.hmac_secret) // Generated once during school creation: bin2hex(random_bytes(32)) public function generateQRToken(Student $student): string { $school = $student->school; $payload = "{$student->uid}|{$school->academic_year}"; $token = hash_hmac('sha256', $payload, $school->hmac_secret); $student->update([ 'qr_token' => $token, 'qr_token_year' => $school->academic_year, ]); // QR code content: "{UID}|{TOKEN}" return "{$student->uid}|{$token}"; } // Properties: // - Deterministic: same input = same token (for verification) // - Year-bound: different academic_year = different token // - School-bound: different hmac_secret = different token // - Compact: 64-char hex string fits easily in QR code

Verification Flow

// ONLINE (server verification): POST /api/v1/attendance/verify-qr { "qr_data": "AIA-2026-000412|a3f7c9e2b1d8..." } // Server: // 1. Split by "|" → uid, submitted_token // 2. Find student by uid (BelongsToSchool auto-scopes) // 3. expected = HMAC(uid + academic_year, school.hmac_secret) // 4. Compare: // submitted_token === expected → ✅ VALID // submitted_token === HMAC(uid + prev_year) → ⚠️ EXPIRED (needs renewal) // no match → ❌ INVALID // OFFLINE (Flutter soft-check): // 1. App caches student list with qr_token on last sync // 2. On scan: SQLite lookup by uid // 3. Compare cached qr_token with scanned token // 4. Valid → mark present, queue for server sync // 5. Invalid → show warning, allow manual override

Annual Renewal

  • During Year Promotion Wizard: system regenerates QR tokens for ALL active students
  • New academic_year in payload → completely new token → old cards stop working
  • This forces annual card orders (new QR = new physical card = recurring revenue)
  • HMAC secret stays the same — only the year component changes
  • Token regeneration is a batch job: 500 students in ~2 seconds

Start Small

Your current Contabo VPS ($4.95/mo, 4 vCPU, 8GB RAM, 200GB SSD) is enough for the Growth tier (up to 2,000 students / 10 schools). Don't upgrade until you actually need it. Contabo lets you scale in place — your data stays, the server just gets more resources.

Scaling Decision Points

  • At 10 schools: Consider Redis for session management and queue jobs. Add a CDN for static assets if response times increase.
  • At 25 schools: Move MySQL to a separate server (or managed database like DigitalOcean Managed MySQL). This doubles your available RAM for PHP.
  • At 50+ schools: Add a load balancer and second app server for redundancy. At this scale, downtime costs you real money.
  • At 100+ schools: You need a DevOps person or managed infrastructure. This is no longer a one-person job.

School Onboarding Checklist (SaaS)

With SaaS, onboarding a new school takes ~30 minutes of your time (no hosting setup, no deployment). Everything happens in your Super Admin panel.

#StepTime
1Create school record: name, code, logo, calendar system3 min
2Create School Admin account2 min
3Upload CSV of students (or give template to school)10 min
4Schedule Photo Session (or guide school through Flutter capture)Variable
5Create first card order (auto-generated after photos confirmed)1 min
6Print cards on PVC printer~1 hour for 300 cards
7Ship/deliver cards to school1–3 days

Compared to Per-School Deployment

In v2 (per-school), onboarding took ~72 minutes of technical work (hosting, deployment, migrations, testing). In v3 (SaaS), it's ~20 minutes of admin work. You can onboard 3 schools in the time it used to take for 1. The printing and shipping are the bottleneck now — not the technical setup.
