EduID mobile app — full UI/UX inventory for redesign

Everything currently built in the EduID companion app — every screen, every button, every state — documented screen-by-screen so a designer can take it from here without reverse-engineering the code. This is the app teachers, school admins and parents use daily in Ethiopian schools: scanning ID cards for attendance, viewing schedules and grades, and (for admins) running ID-photo sessions.

Platform Flutter, Android-first (iOS-compatible) Version 1.4.0 Screens documented 14 Roles Teacher · School Admin · Parent

Before you open Figma

What the app is built on, and why it looks the way it does

The current UI was built by an engineer optimizing for low-end Android phones in areas with patchy connectivity — cheap devices, older GPUs, spotty 3G. That drove specific technical choices which constrain (but don't have to limit) the redesign:

  • No blur, no gradients, no glow shadows. Every surface is a flat, solid Material with a hairline border. This was a deliberate performance decision, not a lack of visual ambition — BackdropFilter and large shadows are expensive on old GPUs. A redesign can reintroduce depth, but should budget for a "lite" rendering path on lower-end devices if it leans on blur/shadow heavily.
  • Instant touch feedback everywhere. Every tappable surface is wrapped in InkWell so the ripple starts on pointer-down before any async work resolves. Whatever the new design system is, this principle (instant feedback, never wait for a network response to acknowledge a tap) should carry over.
  • No custom fonts or image assets are bundled today. pubspec.yaml has no fonts: or assets: section — the app renders in the OS default (Roboto on Android, San Francisco on iOS). This is one of the most visible upgrades available: a bundled type family would instantly differentiate the app from generic Flutter apps. Keep bundle-size and glyph-coverage (Latin + nothing exotic needed) in mind.
  • Offline-first, always. Attendance can be captured with zero connectivity — QR verification, marking, and saving all work offline; a background SyncEngine pushes queued data automatically every 3 minutes and immediately after a save. The UI has to communicate sync state (queued / syncing / synced) constantly and honestly — this is not cosmetic, it's core trust with the user. See the SyncBadge component below.
  • Camera-heavy. Two screens are full-camera experiences (QR scanning, ID-photo capture) that must remain fast to open and responsive to hold steady in a classroom.
Brief for the designer — none of the above are aesthetic mandates, they're performance/connectivity constraints. You have real freedom on color, type, iconography, motion and layout. Just keep heavy blur/shadow effects as an "if budget allows" tier rather than the default render path, and treat sync/offline state as a first-class piece of UI, not an afterthought.

Screen catalog

Fourteen screens, documented in the order a new user encounters them. Each entry lists every visible element with its exact current label, every state the screen can be in, and specific notes for what to preserve, what's flagged for improvement, and any edge case the code already accounts for.

SCREEN 01 · COLD START

Splash

lib/main.dart · SplashGate
All roles

First thing anyone sees on cold app launch. Deliberately minimal — one implicit animation, no packages, no image assets — to stay fast on low-end devices. Runs for a fixed ~950ms then hands off to routing.

Elements

  • Logo mark — 84×84 white rounded-square, badge_rounded icon in brand color, centered
  • Wordmark — "EduID", 26px/800, white
  • Tagline — "Smart Student Identity", 13px, 70%-opacity white
  • Full-bleed background = brand primary color (currently emerald)

Motion (current)

  • Logo scales 0.7 → 1.0 over 450ms, easeOutBack curve (slight overshoot)
  • Fades in 0 → 1 over 350ms simultaneously
  • Total hold before handoff: 950ms
Client ask: "professional animated splash, but lightweight." This is the one screen where a bit of personality pays off disproportionately (first impression) — but the client was explicit that low-end device performance matters. Favor a single well-choreographed reveal (logo, then wordmark, staggered) over particle effects, Lottie files, or anything GPU-heavy. No network/asset loading should ever block this screen past ~1.2s.

SCREEN 06 · PUSHED FROM HOME

Attendance Roster

lib/screens/roster_screen.dart
TeacherAdmin

The core daily task. Everyone defaults to Present; the teacher adjusts exceptions (or scans QR cards to verify presence) and saves. Saving queues the session locally and returns to Home instantly — sync happens in the background within ~1 second if online.

Elements

  • App bar title — class name (bold) + live "{N} present · {N} absent" counter beneath it

SCREEN 07 · FULL-SCREEN CAMERA

QR Scanner

lib/screens/scanner_screen.dart
TeacherAdmin

Continuous scan-the-whole-line mode — never leaves the camera between students. 100% offline: the scanned QR payload is verified against the locally cached roster + a cryptographic token, no network round-trip needed.

Elements

  • Full-bleed live camera preview, black background
  • Top bar (over camera) — round close button (×), "Scan student IDs" + class name, round flash-toggle button
  • Center aiming frame — 250×250 rounded square outline; brand color by default, flashes semantic color on each scan result
  • Bottom feedback banner — appears for ~1.1s after each scan: "✓ {name}" (green, success) / "{name} — already marked" (blue) / "Invalid card, or not in this class" (red); default idle text is "Point at the QR code — students are marked present automatically, one after another."
  • "Done" button — full-width white pill at the very bottom, label becomes "Done — {N} scanned" once at least one student is verified

Behavior notes

  • 1.2 second cooldown between scans (prevents one card firing multiple times per second)
  • Duplicate scans in the same session are recognized and flagged distinctly from invalid ones
  • This is a rapid-fire, stand-in-front-of-a-line-of-kids tool — legibility and speed of the flash feedback matters more than subtlety

3 · Auto-lock / PIN security

App backgrounded past the user's chosen timeout (default 5 min; options: immediate / 1 / 5 / 15 / 30 min / never) → next foreground shows PIN unlock instead of the last screen. Works fully offline. Falling back to full password sign-in is always one tap away.

4 · Sign-out with unsynced data

The app actively protects against silent data loss — sign-out is intercepted with a confirmation dialog that names exactly how many attendance sessions haven't uploaded yet and will be lost if they proceed anyway. This safety-net pattern should be preserved (and could be made even more visible/reassuring) in the redesign.

For the redesign to solve

Known gaps & open briefs

Beyond a visual refresh, these are structural/UX issues the client has already flagged or that surfaced during this audit — treat them as part of the brief, not just a paint job.

  • Admin Home currently reuses the Teacher Home screen verbatim. A school admin's job is oversight (how is the school doing today, across all classes) not just "take attendance for my one class." The client specifically asked for a real admin overview: summary charts (attendance rate trend, students missing photos, pending card orders, sync health across the school), not a scan button front-and-center. The Admin Shell already has its own 4-tab structure — Home just needs its own screen design now.
  • Parent has no bottom navigation while Teacher and Admin do — worth deciding whether Parent gets a matching tab bar (e.g. Children / Settings) for consistency, or whether its simplicity is intentional and should be preserved as a deliberately lighter experience.
  • No custom type family or icon set — see Typography section. Highest-leverage single change available.
  • Attendance P/A/L/E buttons and the QR scanner flash-feedback are the two most-repeated, highest- frequency interactions in the whole app (used dozens of times a day per teacher) — they deserve the most design iteration and user-testing of anything here.
  • Motion is currently minimal-to-none outside the splash screen and shimmer skeletons — no page-transition personality, no micro-interactions on the P/A/L/E toggles, scan success flashes, or grade rank badges. The client referenced Duolingo as a tone reference specifically for how satisfying small interactions feel — there's real room here as long as it stays cheap on low-end hardware (favor implicit `AnimatedContainer`/`AnimatedScale`-style transforms over particle/Lottie effects).
  • Settings is one long list — Account, Security, Sync and Sign-out are all stacked on one screen. Fine today at this scale; worth revisiting if more settings get added (e.g. notification preferences).

Tone

Reference direction from the client

The client named Duolingo as a UX/motion reference — not for its visual style (Duolingo is playful/mascot-driven, which doesn't fit a school-administration tool) but for how it makes routine, repetitive actions (a daily lesson, in EduID's case: daily attendance) feel satisfying rather than administrative — clear instant feedback, a sense of progress, momentum. The client also asked for the app's accent to match the public marketing website's emerald green, which is already wired through the app's single color source (AppColors.primary) — changing it site-wide is a one-line change, so feel free to propose a refined shade without worrying about implementation cost.

Where to start

Recommended order: (1) lock a type pairing + full color system, since almost every screen depends on both; (2) redesign the Attendance Roster + Scanner pair, since it's the highest-frequency flow in the app; (3) design the missing Admin Home overview from scratch; (4) apply the new system across the remaining screens using this document as the element-by-element checklist.
